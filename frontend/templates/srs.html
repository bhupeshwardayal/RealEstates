Abstract

This document defines the complete functional and non-functional requirements, architectural blueprints, data models, and verification protocols for the AI-Powered Real Estate Advisor & Property Matcher. The system leverages modern Retrieval-Augmented Generation (RAG) and dense vector search to replace traditional, rigid property filters with an intelligent conversational advisor capable of evaluating complex natural language constraints, calculating financial projections (e.g., loan amortization, EMI), and matching real estate assets with high precision and zero hallucinations.

1. Introduction

1.1 Purpose

The purpose of this document is to specify the complete Software Requirements Specification (SRS) for the development of the AI-Powered Real Estate Advisor & Property Matcher. This document provides technical and functional blueprints for developers, testers, and stakeholders involved in designing, deploying, and evaluating this application.

1.2 Scope of the System

The AI-Powered Real Estate Advisor & Property Matcher is an intelligent, full-stack conversational application that bridges the gap between unstructured human intent and structured property inventory.

  • Accepts conversational, multi-constraint inputs (e.g., budget, commute distance, locality, amenities, layout).
  • Converts property catalogs into semantic vector representations using dense embedding models.
  • Performs low-latency similarity retrieval using in-memory vector indexing (FAISS).
  • Employs Retrieval-Augmented Generation (RAG) to generate grounded recommendations with explicit reasoning.
  • Provides accurate financial calculations, including monthly loan EMIs, price-per-square-foot benchmarks, and projected rental yield.

1.3 Definitions, Acronyms, and Abbreviations

Term Definition
RAG Retrieval-Augmented Generation: An architecture combining information retrieval with large language model generation to ground answers on verified external data.
FAISS Facebook AI Similarity Search: A library for efficient similarity search and clustering of dense vectors.
LLM Large Language Model: Neural network models trained on extensive text datasets to understand and generate human language.
Embedding A high-dimensional numerical vector representation of text capturing semantic relationships.
EMI Equated Monthly Installment: A fixed payment amount made by a borrower to a lender at a specified date each calendar month.
Hallucination A phenomenon where an LLM generates synthetically convincing yet factually incorrect or ungrounded claims.

2. Overall System Description

2.1 Product Perspective

Traditional real estate portals (e.g., 99acres, MagicBricks, Zillow) rely heavily on rigid relational drop-downs (BHK count, exact city name, discrete budget brackets). These fail when a prospective buyer has subjective, multi-faceted requirements such as:

"Looking for a 2 or 3 BHK near an IT park in Pune under 85 Lakhs with good school connectivity and an estimated monthly loan EMI below 50,000 INR."

This project sits on top of relational property data, augmenting it with an intelligent semantic index and conversational interface to address complex conversational queries.

2.2 System Architecture

Tier 1: Presentation

Interactive user interface featuring dynamic chat threads, property card displays, and live financial sliders.

Tier 2: Application / RAG

Manages conversational state, input sanitization, vector query formulation, prompt assembly, and deterministic calculation hooks.

Tier 3: Data & Vector Store

FAISS handles dense vector similarity retrieval for text descriptions; PostgreSQL stores structured property records and logs.

3. Specific Functional Requirements

Module 1: Data Ingestion & Vector Indexing

  • FR-1.1 Data Normalization: The system shall ingest raw property tabular data, clean missing values, and construct unified contextual text blobs containing titles, locations, descriptions, amenities, and floor plans.
  • FR-1.2 Vector Embeddings Generation: The system shall compute vector embeddings for all property records using dense text embedding models.
  • FR-1.3 Index Persistence: The generated vector representations shall be stored in an indexed vector space (FAISS IndexFlatL2 or IndexFlatIP) for sub-second retrieval.

Module 2: Natural Language Query Processing

  • FR-2.1 Intent Extraction: The system shall identify core hard filters (maximum budget, minimum bedrooms, target locality) and soft semantic preferences (ambiance, lifestyle, commute) from raw user queries.
  • FR-2.2 Conversational Memory: The system shall maintain multi-turn dialogue context, allowing users to issue follow-up questions such as "Show me only the ones with covered parking from the above list."

Module 3: Retrieval & Hallucination-Free Generation

  • FR-3.1 Semantic Search Retrieval: Top-K relevant property candidates (default K=4) shall be fetched via cosine / Euclidean vector similarity search.
  • FR-3.2 Grounded Prompt Injection: Retrieved property records shall be injected into a system prompt enforcing a strict negative constraint: "Answer solely based on the provided retrieved context. Do not invent properties, prices, or configurations."
  • FR-3.3 Fallback Handling: If no catalog item matches the criteria, the system shall cleanly inform the user and suggest relaxing constraints.

Module 4: Financial Estimation Engine

FR-4.1 EMI Calculation: The system shall deterministically compute monthly EMI using the standard mathematical formula:

E = P × r × [ (1 + r)^n / ( (1 + r)^n - 1 ) ]

where P is principal loan amount, r is monthly interest rate, and n is total loan months.

FR-4.2 Rental Yield Analysis: Calculate gross rental yield percentage based on median locality rental metrics:

Gross Yield (%) = ( Annual Expected Rent / Total Property Purchase Price ) × 100

4. Data Models & Database Schema

4.1 Relational Entity Schema (PostgreSQL DDL)

CREATE TABLE properties (
    property_id SERIAL PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    locality VARCHAR(150) NOT NULL,
    city VARCHAR(100) NOT NULL,
    price_inr NUMERIC(12, 2) NOT NULL,
    bhk_count INT NOT NULL,
    carpet_area_sqft INT NOT NULL,
    amenities TEXT[],
    possession_status VARCHAR(50), -- 'Ready to Move', 'Under Construction'
    latitude DECIMAL(9, 6),
    longitude DECIMAL(9, 6),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE user_conversations (
    session_id UUID PRIMARY KEY,
    user_query TEXT NOT NULL,
    retrieved_property_ids INT[],
    ai_response TEXT NOT NULL,
    timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

4.2 Vector Store Representation

Each vector node in FAISS corresponds to an individual property_id and contains embedded contextual representations:

Context Chunk = "Property: {title} | Location: {locality}, {city} | 
                Price: INR {price_inr} | Specs: {bhk_count} BHK, 
                {carpet_area_sqft} sqft | Amenities: {amenities} | 
                Description: {description}"

5. Non-Functional Requirements

5.1 Performance & Latency

Vector similarity search across catalog executes in ≤ 50ms. End-to-end response latency ≤ 2.5s.

5.2 Reliability & Accuracy

Financial formulas utilize precise decimal libraries with zero rounding drift. 0% hallucination rate on property pricing.

5.3 Usability & Interface

Mobile-first responsive web design with bright architectural luxury theme, interactive cards, and live calculation sliders.
